# RailScout Recursive Founder-Intent Collaboration Protocol

## Installation status

This is RailScout's local installation of the `@install-recursive-founder-intent-collaboration-protocol` pattern.

- **Repository:** `dababiyoda/RAILSCOUT`
- **Installed for:** RailScout doctrine, workstation behavior, repository decisions, future agent work, and launch-packet generation.
- **Founder intent ledger:** `docs/FOUNDER_INTENT_LEDGER.md`
- **Primary intent records:** `INTENT-0001`, `INTENT-0002`, `INTENT-0003`, `INTENT-0004`
- **Egregore relationship:** subordinate local protocol. UNIIMENTE Kernel controls constitutional governance, cross-organ authority, identity, money, external effects, autonomy, and kill authority.

This local installation exists so the RailScout repository can preserve founder intent and execute disciplined two-pass strengthening even when work happens outside the main UNIIMENTE Kernel repository.

## Objective

For every material RailScout proposal, architecture decision, repository change, validation workflow, or consequential artifact, strengthen exactly twice, preserve the downside record, and convert the result into a lawful execution path.

RailScout must build upward without creating governance theater. The smallest sufficient intervention wins.

## Decision levels

### Lightweight

Use for low-risk maintenance with no material ownership, authority, contract, money, external-effect, evidence-retention, or reversibility impact.

Record:

- intent reference;
- bounded scope;
- validation evidence;
- rollback path.

### Standard

Use for bounded features, refactors, doctrine updates, templates, and material proposals.

Require:

- five-role review;
- baseline, do-nothing option, and competing alternative;
- exactly two upward passes;
- residual risks;
- rollback;
- kill criteria;
- final decision.

### Constitutional

Use for authority, identity, money, external effects, shared contracts, irreversible migration, autonomous capability, or cross-repository governance.

Add:

- complete intent lineage;
- independent evidence review;
- explicit founder decision;
- staged rollout;
- consequence-gate compatibility;
- no execution while approval is pending.

## Required roles

Every Standard or Constitutional decision must record these perspectives separately:

1. **Founder-Intent Steward** - protects the intended outcome and detects interpretation drift.
2. **Systems Architect** - protects boundaries, canonical ownership, contracts, modularity, and whole-system coherence.
3. **Adversarial Reviewer** - attacks hidden premises, failure modes, counterexamples, incentive problems, and abuse paths.
4. **Operator and Maintainer** - evaluates usability, debugging, maintenance burden, handoff quality, observability, and recovery.
5. **Evidence and Welfare Guardian** - evaluates evidence quality, legality, accountability, externalities, reversibility, and participant welfare.

Do not merge role positions into artificial consensus. Preserve material dissent.

## Evidence discipline

For each major claim, identify the evidence tier:

1. prose claim;
2. model output;
3. deterministic fixture;
4. passing unit test;
5. sandbox execution;
6. real external effect;
7. independently verified outcome;
8. commercial result.

A stronger tier proves only the specific claim it supports. A polished document does not prove market demand. A unit test does not prove participant welfare. A founder statement does not prove external reality.

## Pass 1 - structural strengthening

State the intended outcome without embedding the preferred mechanism.

For every credible advantage:

- strengthen it into a larger capability, evidence, coordination, default-path, proof, cost, welfare, or commercial advantage;
- state when that advantage could reverse into a liability.

For every disadvantage:

- remove it;
- bound it;
- make it observable;
- make it reversible;
- convert it into a test, modular boundary, governance advantage, or market signal;
- or preserve it as a reason not to proceed.

Compare the strengthened proposal with:

- current baseline;
- do-nothing option;
- simplest viable alternative;
- strongest competing architecture;
- reversible experiment.

Rejected alternatives must include revival evidence.

## Pass 2 - adversarial compounding

Attack the Pass-1 design as if it were already deployed.

Test for:

- bureaucracy;
- centralization;
- fragility;
- overfit;
- expense;
- incomprehensibility;
- irreversibility;
- contributor gaming;
- dependency on one person, vendor, model, repository, or workflow.

Every Pass-1 disadvantage must receive one disposition:

- `resolved`
- `accepted`
- `deferred`
- `prohibited`
- `experiment`

Include owner and review trigger. A downside may not disappear because wording improved.

## Decision states

Use exactly one final state:

| State | Meaning |
|---|---|
| `RETAIN` | Keep the current or proposed design as dispositioned. |
| `REGRESS` | Return to a prior simpler or safer design. |
| `KILL` | Stop the proposal and preserve the record. |
| `DEFER` | Delay until a named trigger or dependency. |
| `EXPERIMENT` | Run a bounded reversible test. |
| `NEEDS_FOUNDER_DECISION` | Stop consequential action pending authorized judgment. |

The do-nothing option may win. Do not manufacture convergence.

## Completion test

A material RailScout decision is incomplete unless it includes:

- founder-intent reference;
- affected system boundary;
- five-role review;
- baseline, do-nothing option, simplest viable alternative, strongest competing architecture, and reversible experiment;
- exactly two upward passes;
- every Pass-1 disadvantage dispositioned in Pass 2;
- material dissent or explicit no-dissent statement;
- evidence and counterevidence;
- migration or implementation plan;
- rollback path;
- kill criteria;
- decision owner;
- review trigger.

## Safety boundary

RailScout may not use this protocol to authorize itself. If a proposal changes authority, money, external effects, identity, evidence retention, legal posture, or autonomy, it must stop at `NEEDS_FOUNDER_DECISION` until Alfonso or another authorized human approves.

## Local-to-Kernel conflict rule

If this local protocol conflicts with the UNIIMENTE Kernel, the Kernel controls. The conflict must be recorded in the Founder Intent Ledger or a decision record before any consequential work proceeds.

The local protocol may improve RailScout's clarity and execution quality. It may not expand RailScout's authority.
