# RailScout Closed-Loop SOP

This SOP defines how RailScout runs serious work. It exists to prevent strategy theater, hallucinated progress, lost founder intent, and unmeasured activity.

Compressed loop:

```text
Read -> Orient -> Diagnose -> Design -> Attack -> Rank -> Backcast -> Act -> Record -> Measure -> Learn -> Improve -> Queue -> Repeat
```

## Run modes

### Lightweight run

Use for low-risk maintenance, small research checks, or simple artifact updates.

Minimum output:

- inspected evidence;
- action taken or recommendation;
- changed record or no-action trace;
- next action if any.

### Standard run

Use for business architecture, validation planning, repo updates, workflow design, or material doctrine.

Required output:

- objective;
- evidence tiers;
- truth classification;
- system map;
- root constraint;
- alternatives;
- two upward passes;
- decision;
- validation/rollback;
- next action.

### Constitutional run

Use for authority, identity, money, external effects, shared contracts, irreversible migrations, or cross-repo architecture.

Required output:

- complete intent lineage;
- founder/authorized-human decision;
- Kernel compatibility;
- kill criteria;
- staged rollout;
- rollback if possible;
- explicit consequence-gate handling.

## Serious-run procedure

### 1. Read canonical reality

Inspect:

- current north star;
- active opportunity;
- current stage;
- Single Bottleneck Metric;
- prior decision;
- blockers;
- existing evidence;
- current artifacts;
- pending approvals;
- next-action queue.

Do not write first if relevant state exists.

### 2. Determine authority

Rank source authority:

1. Current founder or authorized-human decision.
2. Kernel constitutional governance.
3. Canonical repository files.
4. Primary external evidence.
5. Approved operating records.
6. Recent external evidence.
7. Secondary interpretation.
8. Working assumptions.

Founder aspiration does not automatically become executable authority.

### 3. State the objective

Define:

- what decision or state change is required;
- why it matters now;
- what counts as completion;
- what is intentionally out of scope.

### 4. Collect inputs

Gather only the information needed for the active objective. Avoid research expansion that does not change the decision.

### 5. Separate truth classes

Classify material statements as:

- verified fact;
- supported inference;
- working assumption;
- disputed claim;
- unresolved unknown;
- founder aspiration;
- active requirement;
- implementation;
- external evidence.

### 6. Map the system

Identify:

- participants;
- incentives;
- money flows;
- authority;
- data flows;
- proof requirements;
- dependencies;
- failure points;
- blockers;
- externalities.

### 7. Diagnose root constraint

Ask:

- Where is value trapped?
- What prevents a valid decision?
- Which missing proof causes delay, denial, risk, or rework?
- Which participant bears pain?
- Who has budget and authority?
- What is the narrowest controllable bottleneck?

### 8. Identify the deeper control layer

Determine whether the failure is in:

- product functionality;
- workflow;
- coordination;
- trust;
- eligibility;
- verification;
- routing;
- reconciliation;
- authorization;
- settlement support.

Do not assume software is the answer.

### 9. Generate distinct configurations

Produce materially different routes, not cosmetic variations.

Examples:

- software product;
- managed service;
- diagnostic;
- certification;
- data exchange;
- proof layer;
- embedded payment control;
- institutional standard;
- partnership rail;
- compliance evidence packet.

### 10. Attack and strengthen

Use the RailScout protocol:

- compare proposed design, do-nothing, simplest viable alternative, strongest competing architecture, and reversible experiment;
- perform exactly two recorded upward passes for material decisions;
- preserve dissent and negative evidence.

### 11. Find strongest counterexample

Search for the strongest reason the idea is wrong:

- market already failed;
- incumbent can neutralize;
- buyer has no budget;
- regulatory path blocks;
- cheaper substitute exists;
- integration cost kills adoption;
- risk/liability is unacceptable;
- ethical or participant-welfare harm is real.

### 12. Rank survivors

Score surviving configurations by:

- urgency;
- pain severity;
- budget proximity;
- regulatory tailwind;
- time to external evidence;
- capital intensity;
- data accessibility;
- gross margin;
- incumbent retaliation;
- defensibility;
- interoperability;
- participant welfare;
- wedge-to-operating-system potential.

### 13. Backcast

Define the strongest realistic end state, then work backward:

- end state;
- prior stage gate;
- prior stage gate;
- current gate;
- next action.

RailScout does not leap over gates.

### 14. Choose the smallest consequential action

The action should be:

- lawful;
- bounded;
- measurable;
- reversible where possible;
- cheap enough to run;
- capable of producing decisive evidence.

### 15. Apply authority gate

Classify action as:

- independently executable;
- executable with notification;
- founder approval required;
- Kernel/consequence gate required;
- prohibited.

### 16. Execute or stage

Execute only if authorized. Otherwise, stage a decision packet with evidence, options, risks, recommendation, and required approval.

### 17. Record artifact

Create or update at least one durable record:

- evidence record;
- decision record;
- claim update;
- diagnostic;
- interview guide;
- outreach artifact;
- product spec;
- validation record;
- SOP;
- risk record;
- next-action queue.

### 18. Measure external result

Classify outcome:

- no response;
- rejection;
- objection;
- information supplied;
- introduction;
- meeting booked;
- data access;
- pilot interest;
- signed pilot;
- payment;
- repeat use;
- institutional reliance.

### 19. Update thesis

State:

- what became more likely;
- what became less likely;
- what was disproven;
- what remains unknown;
- confidence level after evidence.

### 20. Route learning

Send learning to the correct record:

- opportunity;
- claims ledger;
- decision ledger;
- SOP library;
- risk controls;
- architecture primitives;
- founder review;
- system improvements.

### 21. Improve the refinery

If the run exposed bad schema, unclear authority, missing evidence, duplicated work, bad metrics, or repeated failure, improve the system itself.

### 22. Queue exactly one next action

End with one next action. No unbounded option cloud.

## Completion standard

A serious run is complete only when it has:

- inspected relevant state;
- classified evidence;
- made or staged a decision;
- created or changed a durable artifact;
- measured or defined the external evidence target;
- updated learning;
- queued exactly one next action.

If none of those occurred, the run was not complete.
