Convert RailScout from a bare egregore-organ seed repository into a governed AI Research Refinery workspace that upgrades raw founder input into stronger business architecture, falsification tests, validation paths, and executable next actions.

## Evidence tier

- Founder instruction: prose claim / direct founder instruction.

- Runtime behavior: not yet implemented.

## Five-role review

### 1. Founder-Intent Steward

The founder's core intent is clear: RailScout must build upward, not passively process ideas. It must treat the ChatGPT Project and repository as cumulative operating material. The doctrine should preserve ambition while preventing accidental authority escalation.

Recommendation: retain the doctrine, explicitly label it non-runtime authority.

### 2. Systems Architect

The repo was nearly empty. A small set of canonical doctrine files creates necessary structure without pretending the system is built. The chosen layout separates prime directive, Backcasting GPS, intent ledger, collaboration protocol, and decision records.

Recommendation: retain a modular documentation seed. Avoid adding runtime scaffolding until artifact schemas are designed.

### 3. Adversarial Reviewer

Risk: the phrase "force thoughts into existence" could be misread as bypassing lawful authorization or external-action gates. Risk: the Build Upward rule could create verbose process inflation. Risk: founder-style language could be mistaken for production capability.

Recommendation: retain only because the files explicitly define the safety boundary and no production autonomy is granted.

### 4. Operator and Maintainer

The doctrine gives the next agent clear operating rules. However, too many governance files can become dead text if not connected to opportunity-packet templates, validation sprints, and launch packets.

Recommendation: retain; next change should create the first opportunity-packet template and avoid expanding doctrine further until used.

### 5. Evidence and Welfare Guardian

The update is safe if it remains doctrine and does not claim external proof. It improves accountability by preserving founder intent and requiring evidence discipline. Welfare is indirect at this stage: future RailScout outputs should improve markets by targeting proof, trust, eligibility, routing, settlement, and coordination failures.

Recommendation: retain with evidence-tier labeling and human authorization boundary.

## Alternatives considered

### A. Do nothing

- **Benefit:** avoids process overhead.
- **Liability:** repository remains a seed with no enforceable workstation logic.
- **Why rejected:** fails the direct founder request to update GitHub and preserve cumulative doctrine.
- **Revival evidence:** if doctrine files consistently reduce execution speed without improving artifacts.

### B. README-only update

- **Benefit:** simplest possible update.
- **Liability:** loses traceability, intent records, and collaboration protocol.
- **Why rejected:** insufficient for material founder-intent preservation.
- **Revival evidence:** if the extra docs are never used by future agents or contributors.

### C. Full runtime scaffold now

- **Benefit:** faster path toward software implementation.
- **Liability:** premature architecture without validated artifact schemas or first workflow proof.
- **Why rejected:** would confuse doctrine installation with production build.
- **Revival evidence:** after first opportunity-packet and validation-sprint schemas are approved.

### D. Chosen: doctrine-layer seed with intent and decision records

- **Benefit:** preserves founder intent, creates operating clarity, and avoids unsupported runtime claims.
- **Liability:** still not a working product.
- **Why selected:** highest leverage for the current repository state.

## Rollback

Revert this branch or the commits that added the doctrine files. Since this change is documentation-only, rollback has no runtime side effects.

## Kill criteria

Kill or regress this doctrine layer if:

- it produces longer outputs without clearer next actions;
- agents use it to avoid falsification;
- it encourages unsupported claims of product capability;
- it increases process burden without producing validated opportunity packets;
- it conflicts with higher-authority UNIIMENTE governance.

## Final decision

`RETAIN`

Retain this as the RailScout repository's first doctrine-layer installation. The immediate next build should be the first opportunity-packet template and validation-sprint template, not further abstract doctrine.
