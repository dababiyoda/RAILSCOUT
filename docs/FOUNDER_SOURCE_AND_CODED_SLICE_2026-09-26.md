## What RailScout is to build

**Founder intent, faithfully normalized:** RailScout is the research and evidence organ of a persistent founder-governed GREG. It converts a bounded real-world signal into cited claims, contradictions, a market-control hypothesis, the strongest falsifier, a defensible decision, and one next action. Its strategic lens is recurring physical-world transactions stalled by broken proof, trust, eligibility, routing or settlement. The first product increment should make that transformation executable and callable by a real governed GREG mission. It cannot claim customer acceptance, market control, an autonomous business, community feedback, or a verified commercial outcome from an internal run.

**Current implementation observation:** RailScout main at inspected tree `017d9f3` contains README and agent instruction files, not an executable refinery. This draft branch now contains a standalone, source-bound appraiser and verifiable receipt; it is not yet a GREG capability or an autonomous refinery. Draft #5 contains extensive doctrine, SOP and an implementation backcast whose next step is templates; #6 is a collaboration pointer. Kernel #114 contains an actual GREG body, capability broker, planner, receipts and a read-only engineering brief on a **draft** branch. Do not build a second Kernel, parallel memory/authority plane, broad agent hierarchy, or a second general-purpose brief engine here. Reconcile #5's valuable source doctrine while advancing the product in code.

### First functional slice: bounded opportunity appraisal

1. **Input:** a signed GREG mission or a directly invoked RailScout local command with a bounded market question and source packet (URL or immutable local file, collection time, rights/access status). No arbitrary web crawl, unsolicited outreach or commitment is implied.
2. **Refinery:** ingest source bytes and metadata; preserve source ID and content hash; extract checkable claims with quoted spans/locations; separate observed fact, allegation, inference and missing evidence; map parties, buyer and budget owner, money flow, proof/eligibility/routing/settlement break, verifier and likely veto. If a source conflicts, retain both claims. Search or accept at least one serious contrary source and expose it. An LLM may propose classifications; deterministic validation and human review govern acceptance.
3. **Decision artifact:** output a versioned Opportunity Appraisal containing claim-to-source links, explicit unsupported premises, strongest counterexample, present business form, narrow pilot, kill criterion, one next action, and five outcome lenses (commercial, strategic, regenerative, institutional, capital). If buyer/budget, affected participant, real verifier or accepted consequence is unknown, status must remain `NEEDS_EVIDENCE`. Do not compute precise TAM or claim a network effect without inputs.
4. **Integration:** expose this as a replaceable RailScout capability invoked from the existing GREG broker and mission journal on #114's trajectory. Consume canonical Kernel contracts or use a narrow adapter with an explicit mismatch list; shared schema/authority changes need separate review. Invocation, budget and future effects remain Kernel-gated. The RailScout result is evidence/proposal, never a grant.
5. **Completion proof:** demonstrate one real, licensed or public source packet and a conflicting/negative source, with a persisted output and independent source-span/hash verification. Run the same mission after interruption; retain the original mission ID, reconcile once, and deliver an intelligible morning report that says what was learned, what failed, and what Alfonso alone must decide. Assert only the achieved evidence tier. The Mac founder-signed VEPMC 0→1 gate in Kernel #117 remains separate.

This slice deliberately mutates a research memo into a **source-bound decision object**: contrary evidence can lower eligibility, the appraisal can return abstention, and later external results can update the same hypothesis without erasing the old version. That reciprocal learning is the mechanism; an LLM summary or extra schema alone is insufficient.

## Coding acceptance and falsifiers

- A caller can run a bounded CLI or capability entrypoint against actual source bytes and receive stable, inspectable output. Document exact run command and observed result in the PR.
- Every material assertion cites an exact source location or is labeled inference/unknown. A fabricated location, changed source byte or missing required source fails verification.
- Conflicting evidence survives serialization; the system can return `NEEDS_EVIDENCE` or `KILL` without generating a bullish opportunity packet.
- A restart cannot mark an unknown external consequence as safely repeated. This first slice has no direct external effects.
- GREG can call the capability under an explicitly granted mission without RailScout obtaining independent authority or copying secrets. If the current PR stack cannot support it yet, ship the RailScout callable behavior first and a small Kernel adapter PR separately; do not claim integration before it runs.
- The demo includes a favorable and an adverse source, source receipt, bounded cost, one next action, and a genuinely new product ability. Passing fixtures or prose alone do not satisfy this criterion.
- Strongest counterexample: a human using a browser and spreadsheet may be faster and cheaper for a single opportunity. Compare a real run against that baseline; retain automation only if it improves evidence fidelity, repeatability or time to a consequential test.

## Two strengthening passes on the proposed slice

**Pass 1 — convert assets and constraints.** The empty RailScout runtime is a narrow clean seam: build one callable read-only appraiser instead of a generic hierarchy. Existing #5 doctrine becomes an evaluative contract rather than another content queue. The lack of autonomous authority yields a tractable source-verification service with a clear Kernel boundary. Downsides: D1 source quality can be poor; D2 a long appraisal can delay customer contact; D3 two repositories increase integration cost. Redesign: D1 retains contrary evidence and abstains on missing verifier; D2 caps the artifact at the next falsifiable decision; D3 keeps one stable capability interface with no mirrored constitution. Compare do nothing (#5 remains prose), templates alone, a generic LLM search agent, and the human spreadsheet baseline on one source packet.

**Pass 2 — attack the redesign.** Source hashing proves bytes, not truth; require independent source interpretation and explicit uncertainty (D1 accepted pending external verifier). A small artifact can omit material stakeholder harm; require the five outcome lenses and record omissions (D2 resolved only for the bounded decision). An adapter can still become a parallel contract; implement one versioned interface and contract parity check, with removal condition if Kernel supplies the contract (D3 experiment). New risks: selective source choice and model-generated citations; test adverse-source inclusion and tamper rejection. Material dissent: the adversarial reviewer prefers a manual pilot until the callable slice beats the baseline; resolve with measured run evidence. Decision: **EXPERIMENT** on the read-only slice; no deployment, merge, spending or external contact authorization follows.

**Five-role review:** intent steward protects the real-product correction; systems architect protects Kernel ownership; adversarial reviewer tests the manual baseline and source gaming; operator demands one runnable command and clear failure mode; evidence/welfare guardian requires adverse evidence, participant effects and honest validation status. This is a review design, not five independent humans signing off.
