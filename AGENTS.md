
Before changing architecture, doctrine, schemas, workflows, repository structure, dashboards, authority paths, app/tool behavior, or external-effect logic:

1. Inspect existing files first.
2. Preserve every material founder intention.
3. Distinguish observation, inference, proposal, aspiration, active requirement, implementation, generated artifact, historical artifact, external evidence, and unresolved claim.
4. Compare the proposed change against do-nothing, simplest viable alternative, strongest competing architecture, and reversible experiment.
5. Run exactly two upward strengthening passes.
6. Preserve dissent, negative evidence, failed tests, duplicates, and terminal-case reasons.
7. Use the smallest sufficient intervention.
8. Record rollback, kill criteria, unresolved risks, and review triggers.

Read `docs/RECURSIVE_COLLABORATION_PROTOCOL.md` and `docs/FOUNDER_INTENT_LEDGER.md` before material changes.

## RailScout OS workstation doctrine

RailScout's workstation is a tool-orchestrating operating system:

- Notion = command memory/control plane.
- Governor Scheduled Runs = heartbeat.
- Tool/App Registry = nervous system.
- Connected apps = bounded execution limbs.
- Cadence Run Notes = audit trail.
- Decision Log = judgment memory.
- Evidence Notes = proof layer.
- Terminal Case Log = zombie-work prevention.
- Duplicate / Revival Queue = repeated-waste prevention.
- Doctrine / Templates = repeatability layer.

No app/tool should be used randomly. Every use must connect to a scheduled run, validation target, opportunity, evidence note, blocker, decision, maintenance task, terminal case, or tool lesson.

## Hard residue rule

A RailScout operator should never use a tool without producing or updating at least one of:

- Evidence Note
- Decision Log entry
- Cadence Run Note
- Validation Target
- Blocker / Constraint
- Tool Lesson
- Opportunity update
- Terminal Case update
- Scheduled Run update

If no structured residue is produced, the work evaporates and should be treated as incomplete.

## Truth and access discipline

Never claim that a workspace, repository, app, page, database, file, issue, branch, PR, or artifact was inspected or changed unless the relevant tool response confirms it.

Use these labels:

- `observed`: actually inspected with a tool.
- `implemented`: actually changed through a confirmed connector/action.
- `proposal`: designed but not applied.
- `unavailable`: blocked by missing endpoint, permissions, or tool surface.

- Do not merge automatically unless explicitly instructed.
